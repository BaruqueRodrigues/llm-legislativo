## 3. Leitura e Validação da Release Curada

O leitor `CuratedReleaseReader` implementa a fronteira de entrada do Python a partir dos dados gerados pela frentre de Curadoria em R/Parquet.

### Invariantes de Validação Aplicadas
1. **Verificação de Publicação Atômica:** Se a pasta de release contiver `COMPLETE.json`, o leitor valida se o hash do arquivo `release_manifest.json` coincide com `manifest_sha256`. Se divergir, a carga é abortada imediatamente.
2. **Validação de Arquivos do Manifesto:** Cada arquivo referenciado em `release_manifest.json` tem seu tamanho em disco e SHA-256 validados antes de qualquer leitura tabular. O leitor suporta `files` serializado tanto como lista quanto como dicionário (`{table_name: file_entry}`), resolvendo caminhos relativos diretamente ou através de `Path(rel_path).name` quando prefixos de staging estiverem presentes.
3. **Validação de Esquema Parquet:** Confere presença e tipagem das colunas obrigatórias nas tabelas `curated_documents` e `split_assignments`.
4. **Integridade de Checksums de Texto:** Para cada documento, calcula `hashlib.sha256(text.encode('utf-8')).hexdigest()` e compara com o valor registrado em `text_sha256`. Rejeita qualquer divergência de hash ou de contagem de `utf8_bytes`.
5. **Filtragem Estrita por Qualidade e Representatividade:**
   - `quality_status == "accepted"` (itens rejeitados ou sob suspeita não entram).
   - `include_in_dataset == True` e `representative_item_id == corpus_item_id` (duplicatas quase-idênticas ou exatas detectadas pela curadoria são descartadas).
   - `split == split_alvo` (isolamento de partição).
6. **Hashes de Proveniência:**
   - `training_item_ids_hash`: $\text{SHA-256}(\text{IDs ordenados separados por quebra de linha})$.
   - `training_text_hashes_hash`: $\text{SHA-256}(\text{concatenação dos hashes individuais de texto})$.
   - `training_bytes`: soma dos bytes UTF-8 consumidos.
7. **Validação em Release Real:** Testado e aprovado com sucesso contra a release curada oficial `data/staging/curation/release_curated_gh_2.0.0` (4 documentos aceitos em train, totalizando 2.820 bytes UTF-8, vocab efetivo de 1.080 tokens e compressão de 4,9474 bytes/token).

## 4. Treinamento BPE Byte-Level e Blindagem de Especiais

### Formulação Teórica e Alfabeto Base
Em conformidade com a decisão D11, o modelo utiliza BPE Byte-Level:
- **Alfabeto Inicial:** Todos os 256 valores possíveis de um byte (`pre_tokenizers.ByteLevel.alphabet()`).
- **Pré-tokenizador:** `ByteLevel(add_prefix_space=False, use_regex=True)`.
- **Decodificador:** `decoders.ByteLevel()`.
- **Especiais:** `PAD=0`, `BOS=1`, `EOS=2`.

### Solução da Blindagem contra Colisões com Textos de Controle
No tokenizer Hugging Face padrão, tokens especiais adicionados via `special_tokens` são inseridos em `added_tokens`. Quando um documento legislativo contém a sequência de caracteres `<pad>` ou `<bos>` (por exemplo, em notas técnicas, discussões de TI ou citações), o tokenizer ingênuo emitiria o ID de controle $0$ ou $1$, distorcendo o contexto causal e introduzindo preenchimento espúrio no meio do documento.

**Solução implementada em `bpe.py`:**
```python
# Após treinar os merges e reservar os IDs 0, 1 e 2 no vocabulário do modelo BPE:
raw_state = json.loads(base_tok.to_str())
raw_state["added_tokens"] = []  # Remove interceptação léxica de especiais
cleaned_tok = Tokenizer.from_str(json.dumps(raw_state))
```

**Resultado verificado formalmente:**
1. `tok.token_to_id("<pad>") == 0`, `tok.token_to_id("<bos>") == 1`, `tok.token_to_id("<eos>") == 2`.
2. Para qualquer texto contendo strings literais como `<pad>`, `<bos>`, `<eos>`, `<unk>`, `[PAD]`:
   - `tok.encode(texto)` tokeniza os caracteres `<`, `p`, `a`, `d`, `>` através dos bytes e merges normais do vocabulário.
   - **Nenhum token ID 0, 1 ou 2 é emitido**.
   - `tok.decode(tok.encode(texto)) == texto` recupera o texto original intacto.
3. IDs de controle só são emitidos de maneira estruturada pelo pipeline de sequenciamento:
   $$\text{Sequência} = [1] + \text{encode}(\text{texto}) + [2]$$
   e posições de preenchimento recebem $0$ (`PAD`).

## 6. Shards `.npy`, Índice Parquet e Derivação de Janelas

### Formato Binário dos Shards
- Arquivos `.npy` contendo array unidimensional com `dtype="<i4"` (inteiro de 32 bits, little-endian).
- Armazenamento puro em disco, sem dependência de serialização Pickle (`allow_pickle=False`).
- Organizados por partição: `tokens/<split>/shard_00000.npy`.
- Cada documento ocupa um intervalo contíguo $[ \text{offset}, \text{offset} + \text{length} )$, iniciando obrigatoriamente com `BOS=1` e encerrando com `EOS=2`.

### Índice Canônico `token_index.parquet`
Gerado com esquema Arrow estrito:
```
corpus_item_id: string (não-nulo)
split: string (não-nulo)
shard_path: string (não-nulo)
offset: int64 (não-nulo)
length: int64 (não-nulo)
text_sha256: string (não-nulo)
utf8_bytes: int64 (não-nulo)
```

### Prova Matemática de Zero Duplicação de Alvos
Para um documento composto por $N$ tokens $[t_0, t_1, \dots, t_{N-1}]$, onde $t_0 = 1$ (BOS) e $t_{N-1} = 2$ (EOS):
- Total de alvos reais de predição: $N - 1$ (todos os tokens a partir de $t_1$).
- Para comprimento de contexto $L=512$, as janelas iniciam em $s \in \{0, L, 2L, \dots\}$ enquanto $s < N - 1$.
- Cada janela $k$ extrai $n_k = \min(L, N - 1 - s_k)$ pares de treino:
  $$\text{input}_k = [t_{s_k}, t_{s_k+1}, \dots, t_{s_k + n_k - 1}]$$
  $$\text{target}_k = [t_{s_k+1}, t_{s_k+2}, \dots, t_{s_k + n_k}]$$

**Propriedades Formais Comprovadas:**
1. $\sum_k n_k = N - 1$: A união de todos os alvos das janelas cobre o documento inteiro sem faltas.
2. $\forall j \ne k, \quad \text{alvos}_j \cap \text{alvos}_k = \emptyset$: Nenhum alvo é previsto mais de uma vez.
3. O último alvo previsto na janela $k$ ($t_{s_k + n_k}$) é exatamente o primeiro token de entrada da janela $k+1$ ($t_{s_{k+1}}$ onde $s_{k+1} = s_k + L = s_k + n_k$).
4. As posições remanescentes de padding à direita ($L - n_k$) recebem:
   - `input_ids = 0` (PAD)
   - `targets = -100` (ignore_index do PyTorch)
   - `attention_mask = False`
   - `loss_mask = 0.0` (float32)

## 7. Dataset, Collator e Integração com PyTorch

### Classes Implementadas em `dataset.py`
1. `TokenDataset`: Subclasse de `torch.utils.data.Dataset`.
   - Carrega `token_index.parquet` e mapeia os shards `.npy` diretamente em memória através de `np.load(path, mmap_mode="r")`.
   - Acesso aleatório O(1) sem necessidade de carregar centenas de megabytes em RAM.
   - Suporta fatiamento instantâneo de janelas contextuais.
2. `make_batch(samples) -> TokenBatch`: Collator canônico para `DataLoader`.
   - `input_ids`: tensor `torch.int64` de shape $[B, L]$.
   - `targets`: tensor `torch.int64` de shape $[B, L]$ preenchido com `-100` no preenchimento.
   - `attention_mask`: tensor `torch.bool` de shape $[B, L]$.
   - `loss_mask`: tensor `torch.float32` de shape $[B, L]$ ($1.0$ para alvos válidos, $0.0$ para PAD).
   - `item_ids`: lista com os identificadores canônicos dos documentos.
   - `window_offsets`: lista com os deslocamentos contextuais $s$.
3. Compatibilidade com `legislm.training.data.Batch`:
   - `TokenBatch.to_training_batch()` realiza a conversão transparente caso o motor de treino requeira a estrutura do subagente 07.

### Teste de Integração Ponta a Ponta com Transformer (`GPTModel`)
Para comprovar que o lote gerado pelo `TokenDataset` e `make_batch` alimenta perfeitamente o modelo sem incompatibilidade numérica:
1. Instanciamos um `GPTModel` educacional com $V=259$, $L=32$, $d=64$, 2 cabeças e 2 camadas.
2. Processamos um lote contendo preenchimento heterogêneo.
3. Calculamos a perda via `F.cross_entropy(logits.view(-1, V), targets.view(-1), ignore_index=-100)`.
4. Executamos `loss.backward()`: todos os gradientes foram calculados com sucesso, com **zero NaNs**, confirmando a total integração entre a frentre 05 (Tokenização), frentre 06 (Modelo) e frentre 07 (Treinamento).

```bash
.venv/bin/python -m legislm.tokenization.cli build \
    --config configs/tokenizer/pilot.yaml \
    --tokenizer-dir data/artifacts/tokenizer \
    --release-dir tests/fixtures/common \
    --output-dir data/artifacts/tokens \
    --context-length 512 \
    --splits train,validation,test
```

**Saída gerada:**
- `tokens/<split>/shard_00000.npy`: Shards binários em `int32` little-endian.

### 3. Subcomando `inspect`
Inspeciona vocabulário, tokens especiais e executa round-trip em tempo real:
```bash
.venv/bin/python -m legislm.tokenization.cli inspect \
    --tokenizer-dir data/artifacts/tokenizer \
```
